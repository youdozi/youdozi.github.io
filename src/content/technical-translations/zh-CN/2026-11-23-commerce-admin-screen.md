**电商后台应帮助运营人员找到需要处理的订单，并看到采取行动所需的证据。** 先建立支付核对、履约和退款跟进队列。在订单详情中并列显示支付结果和该订单的库存预留情况。如果释放预留之后才确认支付，运营人员应能继续暂停发货并跟踪退款请求。

假设一个商家用韩元（KRW）销售实物，从一个仓库发货。本文将系统设计中的最后一件库存示例，以及数据库文章的订单行、预留和支付尝试模型落到后台界面，跟踪运营人员向支付服务商查询已有交易的过程。 [电商系统设计](/en/posts/2026-11-22-commerce-system-design-last-unit-of-stock/) · [电商数据库设计](/en/posts/2026-11-22-commerce-database-design/)

## 让每个菜单都有明确的工作入口

“订单”是日常运营的起点。“支付与退款”和“履约”可直接进入各自的待办。无论从哪里进入，相同订单号都应打开相同的订单详情和历史，方便跨班次、跨团队交接。

| 菜单 | 从这里开始的工作 | 运营人员要看的信息 |
| --- | --- | --- |
| 订单 | 打开支付结果未知、等待履约或退款待处理的订单。 | 订单号、购买时的商品与金额、四项状态 |
| 商品目录 | 修改 SKU 的可售状态、规格或当前价格。 | 各 SKU 当前的销售条件、更改前后的值 |
| 库存 | 查找有库存预留的订单，或根据盘点结果调整差异。 | 各 SKU 的实物库存、预留和分配数量、关联订单、调整历史 |
| 支付与退款 | 核对服务商已有交易并跟进退款请求。 | 支付尝试、服务商交易 ID、原交易金额、查询与退款历史 |
| 履约 | 为订单拣选并发出已分配的商品。 | SKU、数量、是否可发货、发货记录 |
| 角色与权限 | 授予员工查看或处理任务的权限，并审查变更。 | 按任务划分的权限、范围、授予和撤销历史 |

目录价格变动只影响今后的销售。订单详情读取订单行保存的金额。例如，黑色键盘订单 `O-42` 的总额是 43,000 韩元。先确定 2,000 韩元的折扣，再从 42,000 韩元的单价中扣除这笔折扣，加上 3,000 韩元的运费。即使目录价格变更，订单详情和退款审核仍显示购买时的金额。

## 在队列中选任务，在详情中看证据

**支付核对**收集支付结果未知的订单。**等待履约**收集已分配库存、等待处理发货的订单。**退款跟进**收集已记录退款请求、等待最终结果的订单。为每个队列选择排序方式。例如，支付核对可将最早发现的问题排在前面，履约可按仓库截单时间排序。

列表显示订单号、下单时间、商品、金额和当前状态。提供订单号、商品名称或 SKU 搜索和支付状态筛选。在各任务旁显示筛选前的总数，在列表上方显示当前结果数。上线时按需加入日期和负责人筛选，并在关闭详情时保留筛选条件、搜索词和滚动位置。如果更新使原有行从列表中移除，把焦点移回所选任务，让运营人员接着处理下一单。

| 状态 | 显示内容 | 用途 |
| --- | --- | --- |
| 订单 | 待支付、已确认、已取消 | 显示订单进度。已取消订单的支付仍可能延迟确认。 |
| 支付 | 支付未知、已支付、已请求退款、已退款 | 据此决定重查已有交易还是等待退款结果。 |
| 库存 | 已预留、预留已释放、已分配、库存已发出 | 显示为订单锁定的数量和当前状态。 |
| 履约 | 暂停发货、等待履约、已发货 | 显示仓库现在能否发货，或是否已完成发货。 |

订单详情的状态下方直接显示购买时的金额、SKU 与数量、关联的预留 ID 和服务商交易 ID。支付未知时，当前可售库存无法说明该订单是否已经锁定库存。历史记录显示每项变更的时间、操作者、来源及相关 ID。确保窄屏上状态文案清晰，颜色用来强调。

## 支付未知时查询已有交易

订单 `O-42` 的支付请求响应丢失。结果长期未知，员工批准例外，释放预留 `R-42` 并取消订单。支付运营人员打开订单，查询已有交易 `PG-DEMO-42`。确认支付后记录**退款请求**。订单保持取消，发货继续暂停，预留保持释放。服务商确认后再记录退款完成。

图中展示三个虚构订单的分支。`O-43` 的查询未收到响应，因此**支付保持未知、预留继续有效、发货继续暂停**。`O-44` 的支付已确认且预留有效，因此**确认订单、标记已支付、分配库存，将订单移到等待履约**。图只覆盖无响应和支付确认两种情况。生产中，确认交易已关闭且未扣款时，可以释放预留并取消订单。交易信息不一致时，先记录对账异常，再改变状态。

### JavaScript 状态转换示例

示例将查询结果应用到三个支付未知且暂停发货的虚构订单。在浏览器开发者控制台粘贴运行，无需安装任何软件。函数只更新内存中的订单对象。

```javascript
function applyDemoPaymentResult(order, result) {
  if (order.payment !== 'UNKNOWN' || result !== 'PAID') return 'NO_CHANGE';

  if (order.stock === 'RELEASED') {
    order.payment = 'REFUND_PENDING';
    return 'REFUND_REQUESTED';
  }

  if (order.stock === 'HELD') {
    order.order = 'CONFIRMED';
    order.payment = 'PAID';
    order.stock = 'ALLOCATED';
    order.shipping = 'READY';
    return 'READY_TO_SHIP';
  }

  return 'NO_CHANGE';
}

const examples = [
  ['O-42', 'CANCELLED', 'RELEASED', 'PAID'],
  ['O-43', 'PENDING_PAYMENT', 'HELD', 'UNAVAILABLE'],
  ['O-44', 'PENDING_PAYMENT', 'HELD', 'PAID'],
];

for (const [id, state, stock, result] of examples) {
  const order = { order: state, payment: 'UNKNOWN', stock, shipping: 'BLOCKED' };
  console.log(id, applyDemoPaymentResult(order, result), ...Object.values(order));
}
```

预期的控制台输出依次显示订单 ID、结果、订单、支付、库存和履约状态。

```text
O-42 REFUND_REQUESTED CANCELLED REFUND_PENDING RELEASED BLOCKED
O-43 NO_CHANGE PENDING_PAYMENT UNKNOWN HELD BLOCKED
O-44 READY_TO_SHIP CONFIRMED PAID ALLOCATED READY
```

此代码在 Node.js 24.13.0 下运行，输出了预期的三行。

## 在服务器实施操作权限和状态检查

给支付人员授予查询已有交易的权限，给仓库人员授予访问发货记录的权限，将例外释放库存或批准退款的权限交给指定审批人。单独授予修改目录价格的权限。订单详情仅返回当前用户可见的相关字段和操作。每次收到操作请求时，API 都要检查身份验证、操作权限、目标订单访问权限及订单当前状态。支付查询 API 在服务器上定位订单关联的已有交易，并核对服务商账号、交易 ID、金额和币种。应用结果时，读取最新订单和关联预留。如果重试与 webhook 同时到达，防止生成重复发货或退款请求。仓库请求发货时，服务器也要重新核对订单、支付均已确认，且库存已分配。

对于查询已有交易等操作，在按钮附近展示交易和操作范围。查询不会产生新的扣款。查询确认支付时，根据预留状态发起退款或把订单移到等待履约。手动退款、例外释放预留等直接影响资金或库存的操作，需要单独的确认与权限。例如，手动退款的确认界面显示**订单 `O-42`、原交易 `PG-DEMO-42`、申请退款 43,000 韩元及原因**。对于已受理的请求，标注“已请求退款”，在服务端审计历史中保存审批人、操作人、请求时间、前后状态、关联交易和结果。若丢失响应，先查询同一请求的状态。

## 空队列与结果未知应显示不同消息

| 情况 | 消息和下一步操作 |
| --- | --- |
| 队列没有订单 | “此任务暂无订单。”允许运营人员打开其他队列。 |
| 搜索或筛选无匹配项 | “没有符合搜索或筛选条件的订单。”允许在当前队列清除条件。 |
| 订单列表加载失败 | “无法加载订单。”保留搜索条件并提供重新加载。如果仍显示旧结果，标明获取时间。 |
| 订单可以打开，但服务商结果未知 | “查询未收到响应。支付结果仍未知，发货继续暂停。”允许再次查询同一交易。 |
| 用户无操作权限 | “支付人员可以查询已有交易。”在当前角色的访问范围内继续显示状态和历史。 |

## 把示例结果反映到工作队列

假设从**支付核对**打开订单，选择**查询已有交易**。如果没有响应，`O-43` 留在“支付核对”，查询历史记录无响应且预留继续有效。为 `O-42` 记录退款请求后，可以在**退款跟进**中找到它。为 `O-44` 分配库存后，可以在**等待履约**中找到它。履约人员能看到订单状态和历史，以及提示由支付人员运行查询的消息。

示例使用预设的订单和支付响应。生产实现需分别处理登录、客户数据、真实的服务商查询与退款，以及仓库系统集成。
