**इस माइग्रेशन में Kotlin, WebFlux और कोरूटीन से Java, Spring MVC और वर्चुअल थ्रेड पर जाते हैं।** डिलीवरी के लिए समय कम था और मौजूदा टीम को Kotlin सीखनी पड़ती। Java चुनने में समयसीमा और सीखने के खर्च की भूमिका थी। सर्वर पर अनुरोध चलाने के लिए वर्चुअल थ्रेड के साथ MVC चुना गया।

भाषा चुनने की व्यावहारिक वजह और वर्चुअल थ्रेड का प्रदर्शन पर असर अलग सवाल हैं। नीचे का कोड बदलाव का स्वरूप दिखाता है। इसमें प्रोडक्शन कोड या वहाँ मापे गए परिणाम दोहराए नहीं गए हैं।

यह गाइड Java 21 या बाद के संस्करण और Spring Boot 3.2 या बाद के संस्करण में चरणबद्ध माइग्रेशन बताती है। अधिक थ्रूपुट या कम लेटेंसी की गारंटी नहीं है। अनुरोध में बीतने वाले प्रतीक्षा और CPU समय, डेटाबेस कनेक्शन सीमा और डाउनस्ट्रीम क्षमता को ध्यान में रखकर प्रतिनिधि लोड परीक्षण से वास्तविक परिणाम मापें।

<span id="separate-the-three-choices"></span>

## भाषा और निष्पादन मॉडल का फ़ैसला अलग करें

**WebFlux और MVC वेब रनटाइम के विकल्प हैं।** WebFlux का आधार Reactive Streams और एसिंक्रोनस, नॉन-ब्लॉकिंग I/O है। MVC सर्वलेट अनुरोध मॉडल इस्तेमाल करता है। **कोरूटीन Kotlin में एसिंक्रोनस प्रोग्रामिंग का मॉडल हैं**, इसलिए MVC चुनने पर भी `suspend` फ़ंक्शन रख सकते हैं। Spring में MVC और WebFlux दोनों के एनोटेटेड कंट्रोलर Kotlin कोरूटीन समर्थित करते हैं। इसके लिए `kotlinx-coroutines-core` और `kotlinx-coroutines-reactor` चाहिए। [Spring Framework में कोरूटीन समर्थन](https://docs.spring.io/spring-framework/reference/languages/kotlin/coroutines.html)

वर्चुअल थ्रेड Java के हल्के थ्रेड हैं। हर अनुरोध के लिए अलग थ्रेड और ब्लॉकिंग कॉल वाली व्यवस्था में ये प्रतीक्षा करते प्लेटफ़ॉर्म थ्रेड का खर्च घटा सकते हैं। इन्हें चालू करने से JDBC नॉन-ब्लॉकिंग नहीं बनता और डेटाबेस कनेक्शन पूल नहीं बढ़ता। Spring Boot 3.2 या बाद के संस्करण में JDK 21 या बाद के संस्करण पर `spring.threads.virtual.enabled=true` से वर्चुअल थ्रेड इस्तेमाल कर सकते हैं। Boot बेहतर अनुभव के लिए Java 24 या बाद का संस्करण सुझाता है। पिनिंग, पुराने थ्रेड पूल की सेटिंग और डीमन थ्रेड का व्यवहार जाँचने को भी कहता है। [Spring Boot की वर्चुअल थ्रेड सेटिंग और सीमाएँ](https://docs.spring.io/spring-boot/reference/features/spring-application.html)

इस माइग्रेशन में भाषा, वेब रनटाइम और समवर्ती निष्पादन मॉडल एक साथ बदलते हैं। हर बदलाव को अलग जाँचें। तालिका में दिखा स्टोरेज माइग्रेशन अलग निर्णय है। इससे यह निष्कर्ष न निकालें कि वास्तविक सेवा R2DBC इस्तेमाल करती थी या JPA पर गई।

| बदलाव | क्या बदलता है | अलग से क्या जाँचें |
| --- | --- | --- |
| Kotlin → Java | कार्यान्वयन की भाषा और एसिंक्रोनस API का स्वरूप | नल मान, डेटा ऑब्जेक्ट, अपवाद, रद्दीकरण और मौजूदा API अनुबंध |
| WebFlux → MVC | सर्वर पर अनुरोध संसाधित करने का मॉडल | फ़िल्टर, सुरक्षा, अपवाद मैपिंग, SSE और WebSocket |
| R2DBC → JDBC/JPA (यदि ज़रूरी हो) | डेटाबेस पहुँच का मॉडल | ट्रांज़ैक्शन की सीमा, क्वेरी, कनेक्शन सीमा और टाइमआउट |
| कोरूटीन निष्पादन → सिंक्रोनस कॉल और वर्चुअल थ्रेड | काम चलाने और प्रतीक्षा करने का मॉडल | लाइब्रेरी संगतता, ThreadLocal का उपयोग, पिनिंग और संचालन के संकेत |

## किन अनुरोधों का माइग्रेशन करें?

सामान्य अनुरोध-जवाब वाले पथ में JPA या JDBC है और अधिकतर समय डेटाबेस या आगे की HTTP सेवा के जवाब की प्रतीक्षा में बीतता है, तो वर्चुअल थ्रेड के साथ MVC आज़माना उचित है। जिस पथ के अनुबंध में अत्यधिक समवर्ती स्ट्रीम, सर्वर-सेंट इवेंट (SSE), WebSocket या Reactive Streams का माँग नियंत्रण अहम हो, उसे WebFlux पर रखना या अलग करना बेहतर हो सकता है। MVC में `Flow` लौटाने की सुविधा से हर परिवेश में समान स्ट्रीमिंग, रद्दीकरण या बैकप्रेशर व्यवहार की गारंटी नहीं मिलती।

![समयसीमा और सीखने का खर्च देखकर Java चुनें। रिएक्टिव पथ पहचानें। सामान्य अनुरोध को अडैप्टर और सिंक्रोनस स्टोरेज पर ले जाएँ। वर्चुअल थ्रेड और अनुबंध जाँचकर ट्रैफ़िक धीरे-धीरे बढ़ाएँ।](/assets/diagrams/technical/hi-2026-11-01-webflux-coroutines-mvc-virtual-threads.svg)

आरेख सामान्य अनुरोध का माइग्रेशन क्रम दिखाता है। जिन पथों को अब भी स्ट्रीमिंग चाहिए उनका माइग्रेशन टालें और उन्हें बनाए रखें या अलग करें। परीक्षण और अवलोकन मानदंड पूरे करें तभी ट्रैफ़िक बढ़ाएँ। आधार माप की तुलना में परिणाम बिगड़ें तो पुराने पथ पर लौटने का रास्ता रखें।

## Kotlin कोरूटीन कंट्रोलर को Java MVC पर ले जाएँ

ये अंश एक ऑर्डर खोजने वाला एंडपॉइंट दिखाते हैं। माइग्रेशन से पहले Kotlin कंट्रोलर `suspend` फ़ंक्शन के ज़रिए सेवा की प्रतीक्षा करता है।

```kotlin
@RestController
class OrderController(private val orders: OrderService) {
    @GetMapping("/orders/{id}")
    suspend fun get(@PathVariable id: Long): OrderDto = orders.get(id)
}
```

माइग्रेशन के बाद Java MVC कंट्रोलर सिंक्रोनस सर्विस मेथड बुलाकर वही जवाब DTO लौटाता है। धारणा है कि `orders.get(id)` का अनुबंध भी सिंक्रोनस हो चुका है और Java से बुलाया जा सकता है। Java से सीधे Kotlin का `suspend` मेथड नहीं बुलाया जाता।

```java
@RestController
public class OrderController {
    private final OrderService orders;

    public OrderController(OrderService orders) {
        this.orders = orders;
    }

    @GetMapping("/orders/{id}")
    public OrderDto get(@PathVariable("id") Long id) {
        return orders.get(id);
    }
}
```

Spring के एनोटेशन `org.springframework.web.bind.annotation` से आते हैं। `OrderService` और `OrderDto` ऐप की सेवा और जवाब के प्रकार हैं। ये अंश अपने आप चलने वाला पूरा ऐप नहीं हैं। नीचे की Boot सेटिंग से वर्चुअल थ्रेड चालू करें और वास्तविक HTTP अनुरोध के दौरान निष्पादन जाँचें।

जाँचें कि Kotlin के nullable प्रकार Java में कैसे व्यक्त होंगे और `data class` की समानता तथा सीरियलाइज़ेशन का अनुबंध कैसे रहेगा। कोरूटीन की `async` कॉल को क्रमिक Java कॉल से बदलने पर डाउनस्ट्रीम अनुरोधों का क्रम और जवाब का समय बदल सकते हैं। समानांतरता, टाइमआउट और रद्दीकरण अलग जाँचें। केवल मौजूदा कोरूटीन कॉल को `runBlocking` में लपेट देने से सिंक्रोनस Java सेवा में माइग्रेशन पूरा नहीं होता।

Spring MVC खुद Kotlin के `suspend` और `Flow` को समर्थित करता है, इसलिए MVC के लिए कोरूटीन हटाना अनिवार्य नहीं है। इस मामले में **समय कम था और मौजूदा टीम को Kotlin सीखनी पड़ती, इसलिए लक्ष्य भाषा Java थी**। कंट्रोलर और सेवा के अनुबंध भी उसी दिशा में बदलते हैं।

## रिपॉज़िटरी का माइग्रेशन अलग जाँचें

यदि डेटाबेस पहुँच का मॉडल भी बदलना हो तो अगला अलग उदाहरण Kotlin में R2DBC के `CoroutineCrudRepository` से Java में Spring Data JPA पर जाना दिखाता है। सभी पंक्तियाँ मेमोरी में जमा करने की जगह परिणाम सीमित रखें। पुराने API का क्रम, पेज आकार और अधिकार संबंधी फ़िल्टर बनाए रखें।

```kotlin
interface OrderRepository : CoroutineCrudRepository<Order, Long> {
    fun findByCustomerId(customerId: Long): Flow<Order>
}
```

सिंक्रोनस JPA रिपॉज़िटरी एक बार में एक पेज पढ़ सकती है।

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    Page<Order> findByCustomerId(Long customerId, Pageable pageable);
}
```

ये अंश रिपॉज़िटरी का स्वरूप दिखाते हैं और अपने आप में पूरा ऐप नहीं हैं। वास्तविक प्रोजेक्ट में एंटिटी फ़ेच रणनीति, ट्रांज़ैक्शन का दायरा, N+1 क्वेरी, स्थिर पेज क्रम और पुराने `Flow` को रद्द करने या आंशिक रूप से पढ़ने का व्यवहार भी जाँचें। सीमित जवाब वाले एक API से शुरू करें। बाकी पथ बदलने से पहले अनुबंध परीक्षण जोड़ें और क्वेरी देखें।

## वर्चुअल थ्रेड चालू करके जाँचें

Spring Boot 3.2 या बाद के संस्करण और JDK 21 या बाद के संस्करण पर यह सेटिंग लगा सकते हैं।

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

सेटिंग लगाने के बाद जाँचें कि अनुरोध सँभालने वाला थ्रेड सच में वर्चुअल है। अस्थायी निदान के लिए MVC इंटरसेप्टर या कंट्रोलर में `Thread.currentThread().isVirtual()` दर्ज करें। इससे केवल उस अनुरोध पथ की पुष्टि होती है। सभी कार्य या कोरूटीन डिस्पैचर वर्चुअल थ्रेड इस्तेमाल करते हैं, यह सिद्ध नहीं होता।

Java कंट्रोलर में यह एक्सप्रेशन वर्तमान अनुरोध थ्रेड जाँचता है।

```java
public class RequestThreadProbe {
    public static boolean isVirtual() {
        return Thread.currentThread().isVirtual();
    }
}
```

Boot के अनुसार वर्चुअल थ्रेड के साथ थ्रेड पूल प्रॉपर्टी का असर पहले जैसा नहीं रह सकता। कुछ synchronized खंडों या नेटिव कॉल में पिनिंग से थ्रूपुट प्रभावित हो सकता है। अधिक वर्चुअल थ्रेड चलाकर डेटाबेस कनेक्शन या डाउनस्ट्रीम समवर्ती कॉल की सीमा पार करने की कोशिश न करें। पूल उतना ही बड़ा रखें जितना डेटाबेस सँभाल सकता है। कनेक्शन पाने, क्वेरी, डाउनस्ट्रीम कॉल और पूरे अनुरोध की समयसीमाएँ तय करें।

## चरणों में माइग्रेट करें और वापसी के मानदंड तय करें

1. **आधार माप दर्ज करें।** प्रतिनिधि एंडपॉइंट पर समान लोड में अनुरोध दर, p50/p95/p99 लेटेंसी, त्रुटि दर, CPU, हीप, डेटाबेस पूल की प्रतीक्षा और डाउनस्ट्रीम कॉल लेटेंसी इकट्ठी करें।
2. **रिएक्टिव व्यवहार पर निर्भर पथ चिह्नित करें।** SSE, WebSocket, असीमित स्ट्रीम, बैकप्रेशर या Reactive Streams ऑपरेशन पर निर्भर पथों को शुरुआती माइग्रेशन से बाहर रखें।
3. **सीमित जवाब वाला एक API बदलें।** Kotlin से Java में बदलते समय सर्वर रनटाइम और आवश्यक स्टोरेज बदलाव अलग जाँचें। फिर अनुरोध, जवाब, त्रुटि, रद्दीकरण और प्राधिकरण के अनुबंधों का परीक्षण करें।
4. **वर्चुअल थ्रेड पर निष्पादन जाँचें।** परिनियोजन प्रॉपर्टी के साथ वास्तविक रनटाइम थ्रेड और JDBC कॉल का पथ देखें। बैकग्राउंड कार्यों के एक्ज़ीक्यूटर अलग जाँचें।
5. **समान लोड पर तुलना करें।** डेटा आकार और लोड समान रखकर लेटेंसी का वितरण, त्रुटियाँ, CPU, डेटाबेस की प्रतीक्षा और कनेक्शन उपयोग देखें। CPU-प्रधान काम में वर्चुअल थ्रेड CPU क्षमता नहीं जोड़ते। CPU संतृप्ति भी देखें।
6. **ट्रैफ़िक के छोटे हिस्से से विस्तार करें।** कारोबारी त्रुटियाँ, लेटेंसी, डेटाबेस पूल की प्रतीक्षा या संसाधन उपयोग पहले से तय सीमा पार करें तो विस्तार रोकें और जाँचें या पुराने पथ पर लौटें। टीम अपनी सेवा के SLO और आधार माप के अनुसार सीमाएँ तय करे।

लक्ष्य परिवेश में मापे बिना थ्रूपुट या लेटेंसी में सुधार का दावा न करें। पहले समान इनपुट पर बदला हुआ पथ मापें। सुधार न मिले तो MVC पर जाना अपने आप में लक्ष्य बनाने की ज़रूरत नहीं है।

## निर्णय कैसे लें?

सामान्य अनुरोध-जवाब ट्रैफ़िक में JDBC/JPA इस्तेमाल होता है और कई ब्लॉकिंग कॉल की प्रतीक्षा संभावित अड़चन है, तो एक छोटे पथ पर MVC और वर्चुअल थ्रेड जाँचें। यहाँ Java चुनने का कारण समयसीमा और मौजूदा टीम को Kotlin सीखने का खर्च था। भाषा बदलने को वर्चुअल थ्रेड से थ्रूपुट बढ़ने का प्रमाण न मानें। यदि स्ट्रीमिंग या Reactive Streams का व्यवहार उत्पाद की आवश्यकता है तो थ्रेड मॉडल बदलने के लिए अनुबंध कमज़ोर करने के बजाय WebFlux बनाए रखें। समान लोड पर लेटेंसी, त्रुटियों, डेटाबेस की प्रतीक्षा और संचालन की जटिलता की तुलना करके निर्णय लें।
