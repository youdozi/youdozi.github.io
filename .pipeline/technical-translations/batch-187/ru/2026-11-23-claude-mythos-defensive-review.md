## Выберите доказательства для исправления

Результат Claude Security содержит серьёзность, расположение файла и строк, ветку и коммит доказательств, а также предложение по исправлению. Сначала откройте указанные файлы в **том же коммите**. Если текущая ветка изменилась, отдельно проверьте, отсутствует ли то же правило в текущей версии. [Результаты Claude Security](https://support.claude.com/en/articles/14661296-use-claude-security)

| Что проверить | Вопрос для примера |
| --- | --- |
| Проверенная версия и место | Какого коммита службы запроса возврата и проверки прав касается отчёт? |
| Реальное бизнес-правило | Запрещено ли пользователю только с правом чтения запрашивать возврат даже в своём магазине? |
| Область существующих проверок | Проверяет ли серверный путь запроса и роль, и магазин независимо от отображения кнопки? |
| Необходимые доказательства | Какие файлы или настройки нужны, если общую политику авторизации нельзя прочитать? |

Например, если отчёт предлагает проверить право на запрос возврата, сначала выясните, применяется ли на этом пути общая проверка. Если общая политика недоступна, запишите в результате, какие материалы нужны. Если пропуск подтверждён, определите серверную проверку и связанные тесты как область исправления. Функция **Fix** в Claude Security позволяет продолжить исправление в Claude Code. Если Claude Code in the cloud недоступен, скопируйте предложенный промпт в свой Claude Code. В сеансе используется доступная учётной записи модель. Следующий вымышленный запрос предназначен для применения после проверки файлов и подтверждения правила; замените пути и коммиты соответствующими вашему репозиторию. [Исправление результата](https://support.claude.com/en/articles/14661296-use-claude-security) · [Claude Security](https://claude.com/product/claude-security)

```text
Проверь серверную авторизацию запросов на возврат в изученном коммите
и приложенных файлах.

Бизнес-правило
- Запросить возврат может только ответственный за возвраты того же магазина.
- Право чтения отделено от права запрашивать возврат.
- Роль и магазин пользователя берутся из аутентифицированного контекста сервера.

Сначала проверь, применяется ли общая политика авторизации, и укажи файлы
с доказательствами. Если пропуск подтверждён, минимально измени существующую
проверку. Добавь регрессионные тесты: разреши ответственного того же магазина,
отклони пользователя только с чтением, ответственного другого магазина и
неаутентифицированный запрос. Сообщи о проверенных файлах, изменениях,
выполненных тестах и результатах и о том, что осталось непроверенным.
```

Работа завершена, когда **разрешённая область соответствует существующему правилу**. Проверка только роли может пропустить ответственного из другого магазина, а проверка только магазина не исключит пользователя с правом чтения. Изучите изменения и убедитесь, что сервер сравнивает контекст аутентифицированного пользователя с магазином заказа, прочитанного из репозитория.

## Проверьте разрешённые и отклонённые пути

Следующий код отдельно проверяет только решение об авторизации после исправления. Предполагается, что аутентификация и поиск заказа завершены, а сервер передаёт `actor` и `order`. Фактическое выполнение возврата и обмен с платёжным провайдером не входят в область функции.

```javascript
import assert from "node:assert/strict";

function canRequestRefund(actor, order) {
  return actor !== null &&
    actor.role === "REFUND_MANAGER" &&
    actor.storeId === order.storeId;
}

const order = { storeId: "store-a" };
const manager = { role: "REFUND_MANAGER", storeId: "store-a" };

const cases = [
  ["same-store refund manager", manager, true],
  ["read-only operator", { ...manager, role: "VIEWER" }, false],
  ["different-store refund manager", { ...manager, storeId: "store-b" }, false],
  ["unauthenticated request", null, false]
];

for (const [label, actor, expected] of cases) {
  assert.equal(canRequestRefund(actor, order), expected, label);
  console.log(`PASS ${label}`);
}
```

Код сохранён как `refund-policy.mjs` и запущен командой `node refund-policy.mjs`: на Node.js 22.17.0 все четыре решения совпали с ожидаемыми.

```text
PASS same-store refund manager
PASS read-only operator
PASS different-store refund manager
PASS unauthenticated request
```

В реальном репозитории также проверьте, что путь запроса возврата использует это решение. Интеграционные тесты должны проверить, что отклонённый запрос не регистрирует возврат, а разрешённый сохраняет существующий процесс. При закрытии результата запишите коммит или PR исправления, выполненные тесты и оставшиеся задачи. Если отчёт признан ошибочным, запишите и основания, например уже существующую общую проверку.
