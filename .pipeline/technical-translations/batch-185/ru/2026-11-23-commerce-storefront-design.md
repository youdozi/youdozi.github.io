**Если покупатель после оплаты попадает на пустую страницу, ему прежде всего нужно узнать, списали ли деньги.** Покажите экран, на котором можно проверить результат для уже созданного заказа. От карточки товара до истории заказов связывайте на каждом экране то, что уже можно подтвердить, с доступным покупателю действием.

В [руководстве по интерфейсу управления магазином](/en/posts/2026-11-23-commerce-admin-screen/) оператор открывает заказ с неподтверждённым платежом. Здесь рассмотрим ту же ситуацию со стороны покупателя. У магазина один продавец, который продаёт физические товары за южнокорейские воны и отправляет их покупателям. Покупатели оформляют заказы через учётную запись. Правила скидок и доставки приведены для примера.

## Что покупатель решает на каждом экране?

| Экран | Что показать в первую очередь | Что покупатель может сделать дальше |
| --- | --- | --- |
| Каталог и поиск | Названия и фотографии товаров, цены для сравнения и активные фильтры | Уточнить результаты или открыть карточку товара |
| Карточка товара | Цена и наличие выбранного варианта, условия доставки | Выбрать вариант и количество, добавить в корзину |
| Корзина | Вариант, количество и сумма по каждому товару, предварительный итог и товары, препятствующие оформлению | Изменить количество и состав корзины и перейти к оформлению |
| Оформление заказа | Адрес и стоимость доставки, скидки, конечная сумма и ссылки для изменения данных | Проверить условия и перейти к оплате |
| Карточка заказа | Номер, статусы оплаты, доставки и возврата денег, история изменений | Узнать результат или отследить отправление в зависимости от статуса |

Если каталог показывает «От 39 000 ₩», покажите точную цену сразу после выбора варианта в карточке товара. Отмечайте распроданные варианты текстом. Если поиск ничего не нашёл, покажите активные фильтры и дайте возможность их сбросить. Если поиск не загрузился, предложите повторить запрос.

Применяйте правило из [руководства по резервированию товаров](/en/posts/2026-11-22-commerce-system-design-last-unit-of-stock/). В карточке показывайте остаток на момент запроса. В корзине храните выбор покупателя. Сервер резервирует товар, когда создаёт заказ. Если кто-то первым зарезервировал последнюю единицу, отметьте в корзине затронутый товар и вариант, сохранив остальные товары и введённый адрес доставки.

## Разрешите проверить и изменить данные перед оплатой

Рядом с конечной суммой дайте покупателю возможность проверить и изменить варианты, количество и адрес доставки. Назовите кнопку по действию, например **«Оплатить 43 000 ₩»**. Рекомендации WCAG по предотвращению ошибок в финансовых операциях описывают, как дать пользователям возможность проверить и исправить сведения перед отправкой. [Рекомендации W3C по предотвращению ошибок в финансовых операциях](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)

Если при добавлении в корзину клавиатура стоила 39 000 ₩, а при оформлении стоит 42 000 ₩, назовите конкретный товар. Например, «Цена чёрной клавиатуры изменилась с 39 000 ₩ до 42 000 ₩». Пересчитайте скидки и доставку, покажите новую сумму и дайте покупателю подтвердить её до запроса платежа. При создании заказа сервер сверяет согласованный расчёт с суммой списания и записывает условия сделки. [Как база данных магазина сохраняет суммы заказа](/en/posts/2026-11-22-commerce-database-design/)

На мобильном устройстве разместите ссылки для изменения адреса и товаров рядом с соответствующими данными, а конечную сумму — возле кнопки оплаты. Если кнопка закреплена внизу, страница должна прокручиваться достаточно далеко, чтобы покупатель мог прочитать последнее поле и сообщения об ошибках. Вспомогательные технологии могут озвучивать обновления без перевода фокуса, например изменение суммы корзины или результат проверки платежа. Для этого можно добавить `role="status"` к области с обновляемым текстом результата. [Рекомендации W3C по сообщениям о состоянии](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## Проверьте результат платежа на сервере

![Когда покупатель возвращается со страницы оплаты, запросите существующий заказ. Различайте загрузку и ошибку запроса, а затем по состояниям платежа и заказа предложите обновить статус, отследить отправление, перейти к товарам или посмотреть сведения о возврате денег.](2026-11-23-commerce-storefront-design.svg)

Когда покупатель возвращается со страницы оплаты, найдите существующий заказ на сервере. Если после нажатия «Оплатить» ответ о создании заказа потерялся, воспользуйтесь тем же ключом запроса заказа, чтобы узнать, приняли ли его. Кратковременная блокировка кнопки может сократить число повторных нажатий. От дубликатов защищают ключ запроса и проверка уникальности на сервере. API карточки и статуса заказа также проверяют, вправе ли текущий покупатель получить доступ к этому заказу.

| Подтверждённое сервером состояние | Сообщение и действие для покупателя |
| --- | --- |
| Не удалось запросить статус заказа | «Не удалось загрузить статус заказа.» → **Загрузить статус заново** |
| Заказ существует, итог платежа неизвестен | «Мы проверяем результат оплаты.» → **Обновить статус заказа** |
| Оплата прошла, заказ на проверке | «Оплата прошла. Мы проверяем заказ.» → **Обновить статус заказа** |
| Оплата и заказ подтверждены | «Мы получили ваш заказ.» → **Отследить отправление** |
| Отмена подтверждена, списания не было | «Заказ отменён. Деньги не списаны.» → **Смотреть товары** |
| Оплата подтверждена после отмены, возврат денег в обработке | «Мы обрабатываем возврат денег.» → **Обновить статус возврата** |
| Возврат денег подтверждён | «Деньги возвращены.» → **Посмотреть сведения о возврате** |

По фактическому состоянию отгрузки показывайте, готовится ли заказ, находится в пути или уже доставлен. Показывайте кнопку отмены или возврата товара только после проверки, что действие разрешено в этом состоянии, а у покупателя есть соответствующее право. Отображайте ход обработки после принятия запроса. Сообщайте о завершении возврата денег, когда сервер подтвердит результат.

## Свяжите состояния сервера с сообщениями и действиями

Пример принимает состояния заказа и платежа, уже полученные с сервера, и сопоставляет им заголовок и следующее действие. Ошибка сети и неизвестный результат оплаты — разные входные данные. При неопределённом сочетании состояний функция никогда не показывает успех. В коде используются корейские строки интерфейса, а в таблице выше приведены русские соответствия. Сохраните код как `order-view.mjs` и выполните `node order-view.mjs`.

```javascript
const labels = {
  loading: ["주문 상태를 불러오는 중입니다.", null],
  unavailable: ["주문 상태를 불러오지 못했습니다.", "주문 상태 다시 불러오기"],
  pending: ["결제 결과를 확인 중입니다.", "주문 상태 새로고침"],
  paidReview: ["결제는 완료됐고 주문을 확인 중입니다.", "주문 상태 새로고침"],
  confirmed: ["주문이 접수됐습니다.", "배송 상태 보기"],
  closed: ["주문이 취소됐으며 결제된 금액이 없습니다.", "상품 다시 보기"],
  refundPending: ["환불을 처리 중입니다.", "환불 상태 새로고침"],
  refunded: ["환불이 완료됐습니다.", "환불 내역 보기"]
};

function orderView(snapshot) {
  if (snapshot.kind === "loading") return labels.loading;
  if (snapshot.kind === "unavailable") return labels.unavailable;

  const { order, payment } = snapshot;
  if (order === "CANCELLED" && payment === "REFUND_PENDING") {
    return labels.refundPending;
  }
  if (order === "CANCELLED" && payment === "REFUNDED") {
    return labels.refunded;
  }
  if (order === "CANCELLED" && payment === "CLOSED_UNPAID") {
    return labels.closed;
  }
  if (order === "CONFIRMED" && payment === "PAID") {
    return labels.confirmed;
  }
  if (order === "PENDING_PAYMENT" && payment === "PAID") {
    return labels.paidReview;
  }
  if (order === "PENDING_PAYMENT" &&
      (payment === "PENDING" || payment === "UNKNOWN")) {
    return labels.pending;
  }
  return labels.unavailable;
}

const verified = (order, payment) => ({ kind: "loaded", order, payment });
const cases = [
  [{ kind: "loading" }, "loading"],
  [{ kind: "unavailable" }, "unavailable"],
  [verified("PENDING_PAYMENT", "UNKNOWN"), "pending"],
  [verified("PENDING_PAYMENT", "PAID"), "paidReview"],
  [verified("CONFIRMED", "PAID"), "confirmed"],
  [verified("CANCELLED", "CLOSED_UNPAID"), "closed"],
  [verified("CANCELLED", "REFUND_PENDING"), "refundPending"],
  [verified("CANCELLED", "REFUNDED"), "refunded"],
  [verified("CONFIRMED", "UNKNOWN"), "unavailable"]
];

for (const [input, key] of cases) {
  if (orderView(input) !== labels[key]) throw new Error(key);
  console.log("PASS", key);
}
```

Все девять наборов входных данных прошли проверку на Node.js 22.17.0. Ошибка запроса, неизвестный итог платежа, отмена без списания и ожидающий возврат дали ожидаемые сообщения и действия. Проверялась функция, которая выбирает сообщения и действия интерфейса по состоянию. Удобство на мобильных устройствах, работу вспомогательных технологий и интеграцию с реальной системой оплаты проверяют на реализованных экранах.
